# DJC 관리자 P1-01 보안 영속성 기반 검증

## 결과

V8에 관리자 계정·권한·해시 세션·감사 로그·멱등키·상태 이력 8개 테이블을 추가했다. `users`, `companies`, `job_posts`에는 낙관적 잠금용 `version`을 추가하고, 공고 원본 수집 상태와 관리자 노출 상태를 분리하기 위해 `job_posts.moderation_status`를 추가했다.

관리자 계정, 회전 가능한 세션, append-only 감사 이벤트의 JPA 도메인과 저장소를 구현했다. 세션 원문, CSRF 원문, MFA 평문은 저장하지 않는 컬럼 계약으로 제한했다.

## 보안 및 데이터 계약

- 관리자 이메일은 소문자로 정규화하며 DB의 `utf8mb4_unicode_ci` 유니크 제약으로 대소문자 중복을 차단한다.
- refresh/CSRF 값은 64자 SHA-256 hex만 도메인에서 허용한다.
- MFA 비밀은 최대 512바이트 암호문과 키 식별자만 저장한다.
- 감사 로그의 `actor_admin_id`는 의도적으로 FK를 두지 않아 관리자 계정 삭제 후에도 행을 보존한다.
- 상태 이력은 대상과 관리자 FK를 유지하며 삭제보다 비활성화를 기본 운영 정책으로 삼는다.
- `@Version` 충돌은 후속 P2 API에서 HTTP 409 계약으로 변환한다.
- `moderation_status`는 현재 조회 경로에 아직 적용하지 않는다. P2 공고 조치 API와 조회 필터를 함께 배포하기 전에는 `ACTIVE` 기본값만 사용한다.

## 롤백 절차

V8은 기존 컬럼 삭제나 타입 변경이 없는 additive migration이다. 애플리케이션 롤백 시 V8 스키마는 유지하고 이전 애플리케이션 버전만 재배포한다.

1. 운영 적용 전 `users`, `companies`, `job_posts`와 Flyway 이력을 포함한 백업을 생성한다.
2. 별도 복구 스키마에 백업을 복원해 핵심 테이블 row count와 샘플 checksum을 대조한다.
3. V8 적용 후 오류가 발생하면 이전 애플리케이션으로 롤백하고 신규 관리자 쓰기를 중지한다.
4. 스키마 자체 복구가 필요한 경우 유지보수 창에서 검증된 백업으로 전환한다. 운영 DB에서 V8 테이블/컬럼을 즉시 `DROP`하는 절차는 사용하지 않는다.

## KPI / OKR / 평가셋

- **OKR 연결**: 운영 조치의 수동 DB 변경을 0건으로 만들고, 모든 관리자 변경을 추적 가능한 기반에 연결한다.
- **목표 KPI**: 관리자 세션 원문 저장 0건, 감사 누락 0건, 상태 변경 동시성 손실 0건.
- **평가셋**: 도메인 단위 4건, V8 clean/upgrade/제약/감사보존 4건, JPA 저장소 3건, 기존 백엔드 전체 테스트 509건.
- **Before**: 관리자 전용 계정·세션·감사 테이블 0개, 세 핵심 Aggregate의 version 컬럼 0개, 공고 moderation 상태 0개.
- **After**: 관리자 기반 테이블 8개, version 컬럼 3개, 공고 moderation 컬럼 1개, 관리자 핵심 저장소 3개.
- **합격 기준**: 컴파일 성공, 도메인 테스트 4/4, 기존 비환경 의존 회귀 0건, MySQL 26.7 평가 7/7.
